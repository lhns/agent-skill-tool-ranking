# Agent instructions for this repo

This repo triages agent skills, plugins and MCP servers for one user. [RUBRIC.md](RUBRIC.md) is the authority on gates, Fit, tiers, evidence and statuses; read it before rating anything.

## Layout

- `data/entries.toml`: one `[[entry]]` per evaluated skill or tool. The source of truth for sub-scores, verdicts, evidence, review depth, pros, cons.
- `data/categories.toml`: category ids, titles, display order, notes.
- `data/stack.toml`: the Recommended stack, one pick per job with status, load, setup notes, alternates, and for trials `exit_test` and `trial_ends`.
- `ranking/*.md` (categories and `by-job.md`), `PROS-AND-CONS.md` and the marked sections of `README.md`: generated by `python scripts/build.py`. Never edit them by hand; CI fails if they drift.
- Hand-written: the rest of `README.md`, `RUBRIC.md`, `HOW-TO-USE.md`, `DISCOVERY-SOURCES.md`, `INBOX-AND-WATCHLIST.md`, `EXPERIENCE-LOG.md`, `CHANGELOG.md`.

## Trials before intake

Check the Experience log first. If no trial result was logged within the last 30 days, a new candidate gets a short entry only: gate check, facts, tier. Don't debate sub-scores or change the stack, and remind the user which trials are open.

## Adding or re-checking an entry

1. Verify facts on the live repo (license, last commit, first commit, install method, telemetry and its switch). Mark anything you couldn't check as unverified. Never invent repos or numbers.
2. Record how deeply you looked in `review`: `readme`, `search` (README plus keyword search of the code) or `code` (you read the code). Don't write "read" when you searched.
3. Gate-check. A failed gate gets `gate` and `gate_reason` instead of sub-scores.
4. Set `reviewed` (today) and, when you know it, `created` (first commit). Under 30 days old at review means verdict Watch or Skip.
5. Sub-scores 0 to 4 against the rubric anchors. Fit is a guess unless the user set it (`fit_by = "user"`); say so and ask. Cost is context cost only. Leave Effectiveness and Reliability at 1 without a logged trial.
6. `evidence`: E0 or E1 without a trial; E2 needs `evidence_source`; E3 needs an Experience log row. `trust = "official"` or `"own"` where it applies; it gives no bonus.
7. `verdict`: `Optional`, `Watch` or `Skip`, with `: reason` (required in substance for Watch and Skip). The tier is derived. If the entry competes for a stack job, name it in `jobs = ["<job>"]` or cite the pick's ID in `overlaps`.
8. Fill `stars` (say unverified if so), `pros`, `cons`, `overlaps` with short, specific facts.
9. Run `python scripts/build.py`, then `python scripts/build.py --check`.
10. Add one `CHANGELOG.md` row per changed entry, newest first: date, ID, change, triggering evidence.
11. Only change `data/stack.toml` when the user asks or a logged trial justifies it. Entries in the stack carry no `verdict`.

## Logged trials

When the user reports hands-on use: add an Experience log row (date, ID, model, task, result against the exit test), raise evidence to E3, set Effectiveness and Reliability only as far as the statements support each one, update the stack status, and move the next "Up next" pick to "Trying now" with an exit test.

The user's Experience log outranks every other source. One bad session is one negative E3 data point, not a verdict.

## Re-rank requests

Follow the re-rank protocol in RUBRIC.md. Re-check only entries with a trigger; don't re-rate the whole table for consistency.

## Writing style

Short, specific, plain. No em dashes anywhere. IDs are stable: never rename an existing ID; add a new entry and mark the old one instead.

## Git

Work on a branch and open a PR unless the user says to push to `main`.
