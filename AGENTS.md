# Agent instructions for this repo

This repo ranks agent skills, plugins and MCP servers for one user. [RUBRIC.md](RUBRIC.md) is the authority on gates, criteria, evidence levels and statuses; read it before scoring anything.

## Layout

- `data/entries.toml`: one `[[entry]]` per evaluated skill or tool. The source of truth for scores, verdicts, stars, pros, cons.
- `data/categories.toml`: category ids, titles, display order, notes.
- `ranking/*.md` and `PROS-AND-CONS.md`: generated by `python scripts/build.py`. Never edit them by hand; CI fails if they drift.
- Hand-written: `README.md` (recommended stack), `RUBRIC.md`, `HOW-TO-USE.md`, `DISCOVERY-SOURCES.md`, `INBOX-AND-WATCHLIST.md`, `EXPERIENCE-LOG.md`, `CHANGELOG.md`.

## Adding or re-scoring an entry

1. Verify facts on the live repo page (stars, license, maintenance, install method). Mark anything you couldn't check as unverified. Never invent repos or numbers.
2. Gate-check first. A failed gate gets `gate` and `gate_reason` instead of scores.
3. Score each criterion 0 to 4 against the rubric anchors. Effectiveness and Reliability may not exceed the evidence cap; `build.py` rejects violations.
4. Fill `stars`, `pros`, `cons`, `overlaps` (short phrases, specific facts: issue numbers, tool counts, licenses).
5. Run `python scripts/build.py`, then `python scripts/build.py --check`.
6. Add one `CHANGELOG.md` row per changed entry, newest first: date, ID, change, triggering evidence.
7. If the entry becomes the top pick for a job, or displaces one, update the Recommended stack in `README.md`.

## Re-rank requests

Follow the re-rank protocol in RUBRIC.md: process the Inbox, read Experience log rows newer than the latest Changelog entry, re-score only entries with new evidence or a trigger, score re-checks blind before comparing with the old row. Do not re-score the whole table for consistency.

The user's Experience log outranks every other source. One bad session is one negative E3 data point, not a verdict.

## Writing style

Short, specific, plain. No em dashes anywhere. IDs are stable: never rename an existing ID; add a new entry and mark the old one instead.

## Git

Work on a branch and open a PR unless the user says to push to `main`.
